1.Vizyon

Müşterinin verisi üzerinde, SQL bilmeyen kullanıcının sürükle-bırakla sorgu tasarlayıp sonucu tablo/grafik/dashboard olarak görebildiği; SQL bilen kullanıcının da aynı yerde ham SQL çalıştırabildiği, çok kiracılı bir raporlama ürünü.

Turnusol testi: "Bu rapor işi için IT'ye/geliştiriciye gitmem gerekir mi?" — v1'e girecek her özellik bu sorunun cevabını "hayır"a yaklaştırmalı.

SQLST ile ilişki (kullanıcı kararı, 2026-08-04): tamamen ayrı ürün — kod paylaşımı yok. Taşınan şey desen bilgisidir: lehçe soyutlaması (SQLST v3 deneyimi), lisans denetimi geleneği, roadmap/dilim disiplini, "yarım özellik yok → gizlenir" ilkesi.

3.Çalıştırma modları — "hedef DB'de mi, kendi DB'me çekip mi?"

Kullanıcı sorusu (2026-08-04): "İki özelliği de koysak, config'den seçsek: hedef DB'de çalıştır ya da bir job'la kendi DB'me çekip orada çalıştır — olabilir mi?"

Cevap: evet, olur ve sektörde birebir karşılığı var — Power BI'daki DirectQuery vs Import ayrımı. İki mod da v1'e girer; bağlantı düzeyinde varsayılan + veri haritası düzeyinde geçersiz kılma ile seçilir.

SaaS'ın asıl zorluğu — müşteri DB'sine erişim

Müşteri MSSQL'i genelde şirket ağındadır; bizim bulutumuz ona kendiliğinden ulaşamaz.

  • v1 varsayımı: hedef DB SaaS'tan erişilebilirdir (Azure SQL / internete açık MSSQL / IP whitelist / müşteri VPN'i). Ürün belgeleri bunu kurulum önkoşulu yazar.
  • KDS Ajanı (müşteri ağına kurulan, dışarı doğru bağlantı açan hafif gateway — Power BI On-premises Data Gateway modeli) v1 DIŞI, araştırma kuyruğunda.
  • Mod B bu problemi hafifletir: erişim yalnız senkron job anında gerekir; ileride ajan gelirse aynı job müşteri tarafında koşup veriyi itme (push) modeliyle gönderir — mimari bugünden buna göre çizilir (senkron işi tek modülde toplanır).

İçe alım hattı (v1): Hangfire job → veri haritasında seçilen tablolar → tenant'ın kendi deposuna tam yükleme (truncate+load) → sorgular orada koşar. Zamanlama (cron), son senkron durumu/süresi/satır sayısı UI'da. Artımlı yükleme (rowversion/CDC) v1 DIŞI — araştırma kuyruğu.

4.Veri haritası (eski adı: semantik katman)

Varlık zinciri: Bağlantı → Veri Haritası → Sorgu/Rapor → Dashboard

  • Bağlantı: sunucu + DB + salt-okunur kimlik; şifre şifreli saklanır (§7).
  • Veri Haritası: tasarımcının seçtiği tablolar; dostça adlar (FKTHR_MSTR → "Fatura Ana"); önceden tanımlı ilişkiler (join'ler); kolonlarda boyut/ölçü işareti; çalıştırma modu seçimi (canlı / içe alım).
  • Sorgu/Rapor: JSON sorgu modeli + görselleştirme tercihi; klasörlenir, yetkilenir.
  • Dashboard: raporların grid yerleşimi + dashboard-düzeyi filtreler.

Son kullanıcı ham tabloya değil veri haritasına bakar; ham SQL ayrı ekranda, ileri kullanıcı rolüne açıktır. KDS'lerde başarıyı bu katman belirler — son kullanıcı join kuramaz, kurmamalı; ilişkiyi harita tanımlar, tasarımcı sadece sürükler.

5.Sorgu temsili ve SQL üretimi

Tasarlanan sorgu SQL olarak değil, JSON modeli (AST) olarak saklanır; SQL'e çeviri backend'de, motor lehçesine göre yapılır. Kazanımlar: sorgu versiyonlanabilir/denetlenebilir, UI'dan bağımsız doğrulanabilir, çok-motor kapısı açık kalır.

v1 JSON modeli kapsamı: kaynak varlıklar (modelden) · kolon seçimi · join (modeldeki ilişkilerden) · filtre ağacı (AND/OR, parametreli) · GROUP BY + aggregate (SUM/COUNT/AVG/MIN/MAX) · sıralama · limit/sayfalama.
v1 DIŞI: alt sorgu, UNION, window fonksiyonları → ihtiyaç ham SQL ekranına yönlendirilir.

Hat: React tasarımcı → JSON → doğrulama (şema + model/yetki süzgeci) → ISorguUretici (v1: MssqlSorguUretici) → parametreli SQL → çalıştırıcı.

Kurallar (MersisMSSQL derslerinin mirası): nesne adları daima QUOTENAME mantığıyla parantezlenir; değerler asla birleştirilmez, daima parametre; üretilen SQL kullanıcıya "SQL'i Göster" ile sunulur (şeffaflık + öğrenme + hata ayıklama).

7.Güvenlik

  • SELECT-only bekçisi: Microsoft.SqlServer.TransactSql.ScriptDom (MIT, resmî T-SQL parser) ile AST doğrulaması — string kontrolü değil. Yalnız SELECT statement'ları geçer; çoklu statement, DDL/DML/EXEC, INTO, hint istismarları red. Hem ham SQL ekranı hem üretilen SQL aynı bekçiden geçer (tek kapı).
  • İkinci katman: hedef bağlantılar salt-okunur DB kullanıcısıyla kurulur; ürün belgeleri müşteriden read-only login ister (bekçi delinse bile yazamaz).
  • Bağlantı şifreleri: ASP.NET Data Protection ile şifreli, key ring kalıcı depoda; düz metin hiçbir yerde durmaz (vault entegrasyonu araştırma kuyruğu).
  • Limitler: satır sınırı + zaman aşımı (tenant/sorgu bazlı ayarlanabilir) + tenant başına eşzamanlı sorgu sınırı.
  • Keycloak: tek realm; tenant ayrımı organizasyon/grup + token claim'i; kaba roller token'da (Admin / Geliştirici / Müşteri); rapor/klasör-bazlı ince yetki metadata DB'de.
  • Audit: kim, hangi tenant'ta, hangi sorguyu (JSON/SQL), hangi bağlantıda, ne zaman, kaç satır/ms — her icra kaydedilir.

8.Multi-tenancy

  • Metadata DB: tek DB + her tabloda TenantId + EF Core global query filter.
  • İçe alım deposu: tenant başına ayrı DB — veri izolasyonu, müşteri ayrılınca temiz silme, yedek/geri yükleme kolaylığı, gürültülü komşu sınırı.
  • Keycloak: tek realm (realm-per-tenant bilinçli DIŞI — yönetim yükü).

10.Barındırma ve Kubernetes analizi

Karar: v1'de Kubernetes YOK. Tek VM + Docker Compose: API + Keycloak + MSSQL + React statik dosyaları (+ Hangfire API içinde). SaaS olduğumuz için her şey zaten konteyner imajı — K8s'e geçiş kapısı açık kalır, hiçbir şey yeniden yazılmaz.

K8s'i yeniden değerlendirme sinyalleri (hangisi gelirse araştırma açılır): tek VM'in dikey sınırına dayanmak · SLA gereği çoklu-düğüm/sıfır-kesinti dağıtım · tenant sayısının job+sorgu yükünü ayrı worker'lara bölmeyi gerektirmesi.

12.Başarı ölçütleri (v1)

  1. SQL bilmeyen bir kullanıcı, iki tablolu join'li + gruplu + filtreli bir raporu hiç SQL yazmadan tasarlayıp grafiğe bağlayabilmeli ve dashboard'a koyabilmeli.
  2. Canlı modda 1M satırlık kaynak tabloda tasarımcı sorgusu ilk sayfayı < 3 sn'de getirmeli; hiçbir sorgu satır sınırı/zaman aşımı olmadan koşamamalı.
  3. İçe alım job'ı zamanında koşup aynı raporu tenant deposundan aynı sonuçla vermeli; mod geçişi (canlı ↔ içe alım) raporu bozmamalı.
  4. SELECT dışı hiçbir komut, hiçbir ekrandan/yoldan çalıştırılamamalı — test kanıtlı (bekçi + read-only kullanıcı iki katman ayrı ayrı doğrulanır).
